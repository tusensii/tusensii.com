# Bird Plates — Customizable Facts, Section Headers, and Local Admin UI

Date: 2026-07-22
Status: Approved for planning

## Context

`birds/index.html` renders a series of bird photo "plates" (specimen-card style: photo, species name, binomial, a `<dl class="specs">` list of label/value facts, and a remark). Data lives in `data/plates.json`, a flat array of bird objects with fixed fields (`image`, `alt`, `species`, `binomial`, `locality`, `season`, `behavior`, `remark`). `scripts/build-plates.mjs` injects the array into `birds/index.html` between `<!-- PLATES:START -->`/`<!-- PLATES:END -->` markers, numbering plates with roman numerals by array index. There is no admin UI — all edits are manual JSON + Node script + `wrangler pages deploy`.

This spec covers three additions:
1. A customizable, per-bird facts list (replacing the fixed locality/season/behavior fields).
2. Green section-header dividers (e.g. "Seabirds", "Waterfowl") placed anywhere in the plate order.
3. A local-only admin UI for managing all of the above, including drag-and-drop / numeric reordering, image upload, and a two-stage Save/Deploy workflow.

## Data Model

### `data/plates.json`

Becomes a single ordered array mixing two item types (this ordering *is* the display order — reordering in the admin UI just moves items in this array):

```json
[
  { "type": "section", "title": "Waterfowl" },
  {
    "type": "bird",
    "image": "/images/plates/great-blue-heron.jpg",
    "alt": "Great blue heron in flight against a clear blue sky",
    "species": "Great Blue Heron",
    "binomial": "Ardea herodias",
    "remark": "In flight they look <strong>almost prehistoric</strong> — all wing, barely any bird.",
    "facts": [
      { "type": "locality", "value": "Nisqually National Wildlife Refuge" },
      { "type": "season", "value": "Late spring" },
      { "type": "behavior", "value": "Flying low over the refuge" }
    ]
  }
]
```

Core per-bird fields — `image`, `alt`, `species`, `binomial`, `remark` — are unchanged from today. **Reclassification:** `locality`, `season`, `behavior` move from fixed fields into the `facts` list as pre-seeded catalog entries. This is a deliberate reinterpretation of "keep core fields, add a facts list" based on the user confirming the current `<dl class="specs">` look (Locality/Season/Behavior rows) is exactly the "facts" display they want — so those three become the first three catalog entries rather than staying hardcoded. Each bird's facts (which catalog entries are shown, their values, and their order) are fully independent per plate, including across duplicate-species plates (e.g. the two existing Mallard entries can show different facts).

### `data/fact-catalog.json` (new file)

Master list of known fact types, used to populate the "pick a fact type" control in the admin UI:

```json
[
  { "key": "locality", "label": "Locality" },
  { "key": "season", "label": "Season" },
  { "key": "behavior", "label": "Behavior" },
  { "key": "diet", "label": "Diet" },
  { "key": "habitat", "label": "Habitat" },
  { "key": "wingspan", "label": "Wingspan" },
  { "key": "lifespan", "label": "Lifespan" },
  { "key": "conservation_status", "label": "Conservation Status" },
  { "key": "call_song", "label": "Call / Song" },
  { "key": "migration", "label": "Migration" },
  { "key": "nesting", "label": "Nesting" },
  { "key": "size_weight", "label": "Size / Weight" },
  { "key": "similar_species", "label": "Similar Species" }
]
```

New fact types typed inline while editing a bird are appended here automatically, becoming available for every future bird. A per-bird fact whose `type` isn't in the catalog is still rendered (its `type` string is used verbatim as the label) — the catalog is a convenience picker, not a strict schema.

## Migration

A one-time script (or a manual pass, given there are only 9 plates) converts each existing bird's `locality`/`season`/`behavior` fields into a `facts` array in that order, and wraps the whole thing in the new `{ type: "bird", ... }` envelope. No section headers are introduced by the migration — the user adds those later via the admin UI. No data is dropped; field values map 1:1 into facts of the corresponding catalog key.

## Rendering

### Shared render module: `scripts/render-plate.mjs`

Extracted from the current inline logic in `build-plates.mjs`, exporting functions that both the build script and the admin UI's live preview import — so the preview can never drift from what actually deploys. Must faithfully preserve today's behavior:

- Bird plates: `<article class="plate">` markup identical to today's, with the `<dl class="specs">` block now generated by iterating the bird's `facts` array (label = catalog lookup or verbatim fallback, value = `fact.value`) instead of three hardcoded rows.
- The species `<h2>` line-break rule stays exactly as-is: `p.species.replace(' ', '<br>')` (first space only).
- Plate numbering (`No. I`, `No. II`, ...) continues straight through the whole sequence, **skipping section items** when incrementing the counter — i.e. the counter only advances on `type: "bird"` items.
- Section items render as a full-width `<div class="band"><span>{title}</span></div>` (or similar), reusing the existing `.band` CSS class already in `css/site.css` (spruce-green `var(--field)` background, bold white text, used today for the "interstitial green band"). No new CSS is required for this.

`build-plates.mjs` is rewritten to read the new array shape, call the shared render module per item, and write the joined output between the existing `PLATES:START`/`PLATES:END` markers — the file's overall responsibility (read JSON, splice into template, write HTML) doesn't change.

## Admin UI

### Running it

`node scripts/admin-server.mjs` starts a small Node HTTP server bound to `127.0.0.1` only (no auth — personal local tool, not exposed to the network), serving a single-page vanilla JS/HTML app from a new `admin/` directory. No new frontend framework/build step is introduced, consistent with the rest of the site being framework-free.

### Layout

**Left pane — ordered list.** Shows every item (bird thumbnails + section-header bars) interleaved in actual display order. Each row has:
- A drag handle (drag to reorder).
- An editable position-number input (typing a new number moves the item to that position; stays in sync with drag state).
- Row actions: delete, duplicate (birds only — copies all fields/facts as a starting point for a new plate).
- An "Add bird" and "Add section header" control at the list level, inserting a new blank item at a chosen position.

**Right pane — editor for the selected item.**
- Section header: single `title` text field.
- Bird: image upload/preview (see below), `species`, `binomial`, `alt`, `remark` fields, and a facts editor:
  - List of the bird's current facts, each with its label (from catalog or custom) and value, reorderable.
  - "+ Add fact" control: pick an existing catalog entry, or type a new label to create one on the spot (added to `fact-catalog.json` immediately).
  - Remove a fact from the bird without deleting it from the catalog.

**Live preview.** Alongside the editor, a rendered preview of the currently-selected plate or section band, generated via `scripts/render-plate.mjs` so it's pixel-identical to what `build-plates.mjs` would produce — not a hand-rolled approximation.

### Image upload

Selecting/dropping a file in the admin UI sends it to the local server, which:
- Slugifies the bird's species name (or a user-provided name) into a filename, guarding against path traversal (reject/strip `..`, path separators, and non-alphanumeric characters beyond a safe set).
- Copies the file into `images/plates/` under that filename.
- Fills in the bird's `image` field with the resulting path; `alt` is left for the user to type (no auto-generation).

### Save vs. Deploy

Two distinct actions, deliberately kept separate:

- **Save**: writes the current in-memory state to `data/plates.json` and `data/fact-catalog.json` on disk. Does not touch `birds/index.html`, run any build step, or deploy anything.
- **Deploy** (separate button, behind a confirmation prompt since it pushes to production): runs, in order, `build-plates.mjs` → `version-assets.mjs` → `wrangler pages deploy`, streaming each command's stdout/stderr into the admin UI so a failure is visible rather than silent. No git commit/push is performed as part of Deploy — that remains a manual step if/when the user wants one.

## Out of Scope

- Git commit automation as part of Deploy (explicitly rejected).
- Authentication/password gating on the admin server (explicitly rejected — localhost-only is sufficient).
- Per-species shared fact profiles/inheritance (explicitly rejected — every plate's facts are fully independent).
- Numbering reset per section (explicitly rejected — numbering stays continuous across the whole page).
- Auto-generating `alt` text from uploaded images.

## Testing

- Unit-level: `render-plate.mjs` output for a bird and a section item, verified against a known-good HTML snapshot (including the `<br>` rule and numbering-skips-sections behavior).
- Migration script: run against current `data/plates.json`, diff `build-plates.mjs` output before/after to confirm the regenerated `birds/index.html` is unchanged (no visual regression) aside from the internal data-shape change.
- Manual: exercise the admin UI end-to-end (add/edit/delete/duplicate a bird, add a section header, reorder via drag and via number input, add a custom fact type, upload an image, Save, then Deploy against a throwaway/staging check) before trusting it against the real production site.
